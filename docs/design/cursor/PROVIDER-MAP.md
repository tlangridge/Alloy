# Cursor provider integration map

**Current state:** Alloy already registers a `cursor-agent` adapter, but it is an experimental panel stub: `read_only=False`, no Cursor auth check, `--print --output-format text`, optional model pin, and plain stdout parsing. It is excluded from the default panel and from managed execute. A full Cursor integration would extend or replace this stub; the repository contains no routable `cursor` profile or managed Cursor worker. ## 2. Model families and independence

The exact routing structure is `FAMILIES = {"codex":"openai", "claude":"anthropic", "grok":"xai", "antigravity":"google"}`. A profile’s explicit `"family"` overrides that adapter default; validation currently permits only values present in `FAMILIES.values()`. Thus **one CLI can already carry different families per model**: the code and test do this for an Anthropic model served by agy. Add Cursor to the adapter registry and routing registry, permit `"cursor"` as a family for Composer, and give each Cursor profile its actual family (`anthropic`, `openai`, `google`, `xai` or `cursor`). The CLI’s name must not determine those profiles’ families. ## 5. Checker grants and write boundaries

A Checker uses the adapter’s ordinary read-only invocation; `probe()` rejects any adapter whose `read_only` is false. For agy, Checker read grants are built for the staged prompt, worktree and private gate-log root, while write tools are denied in private settings. Codex uses its read-only sandbox; Claude and Grok use plan permissions. After review, Alloy rejects a changed worktree or HEAD and requires a matching packet ID, revision and complete-context receipt before accepting a pass. These last checks detect failures; they do not themselves prevent writes. [bin/alloy_execution.py:159](bin/alloy_execution.py:159) · [bin/alloy:780](bin/alloy:780) · [bin/alloy:884](bin/alloy:884) · [bin/alloy_execution.py:376](bin/alloy_execution.py:376) · [bin/alloy_execution.py:548](bin/alloy_execution.py:548)

For Cursor, verify that its headless sandbox and approval behavior **actually deny edits and commands without prompting** before marking the adapter read-only or letting a Checker see the real worktree. Keep its `--force`/approval bypass out of panel and Checker argv; implement Maker permissions separately in `worker_adapter()` and its help-flag probe. Current `cursor-agent` has no such verified boundary and is deliberately refused by default; even an explicitly unsandboxed panel gets a disposable repo copy. Managed Maker writes occur in an owned worktree, with post-run allowed-path checks and integration proof.
